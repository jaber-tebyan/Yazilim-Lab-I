== Abstract

This report describes the Campus Resource Reservation System developed for Software Laboratory I.
The system shares scarce campus resources (meeting rooms, laboratories, 3D printers and a GPU server) among students, researchers and technicians under a Resource Point (KP) economy.
Its core is a reservation module that is independent of any user interface: it reads an initial configuration file, executes a JSON Lines command script in order, and writes exactly one result line per command.
The module implements thirteen ordered validation rules, maintenance windows, preparation times, a consecutive-use limit, occupancy-based dynamic pricing with a peak surcharge, a weekly quota, all-or-nothing package reservations, a reservation state machine, a reliability score, and an automatic waiting list.
A deterministic, event-driven simulated clock applies simultaneous events in a fixed order.
All operations pass through one engine entry point, so the command-line path and the desktop application use the same rules.
A data-driven test suite checks each command family and the interactions between the clock, the waiting list and the state machine.

_Index Terms_ -- resource reservation, dynamic pricing, state machine, waiting list, discrete-event simulation, Python.

== Introduction

*Motivation.*
A newly established university has only a few meeting rooms, laboratories, 3D printers and one GPU server.
Under a first-come-first-served policy, a few users can block popular time slots, and users who book a slot but never arrive waste capacity.
The university therefore defined its own sharing rules: payment with weekly-renewed Resource Points, prices that rise with demand, usage rules that depend on the resource type (a printer must cool down and a laboratory must be ventilated between two uses), and a reliability score that rewards users who respect their reservations.

*Problem statement.*
We must implement these rules in a reservation module that works independently of the user interface, and a desktop application that drives the same module.
Hidden test scenarios compare the result lines field by field, so the implementation must be exact (rounding, boundaries, error-code priority, event order) and deterministic.
All parameters (resource types, roles, quotas, resources, maintenance windows, users and the initial clock) come from the start file and are not hard-coded.

*Overview.*
The module is written in Python 3.11 with Pydantic v2 models.
It provides (i) thirteen ordered checks for a reservation request, (ii) pricing in 15-minute slices based on band occupancy, (iii) atomic packages of two to four items, (iv) the states ONAYLI, KULLANIMDA, TAMAMLANDI, IPTAL and GELMEDI with refunds and reliability changes, (v) a reliability-ordered waiting list with automatic assignment, and (vi) a simulated clock that processes weekly resets, completions, no-shows and automatic assignments chronologically.
Section 2 explains the method, Section 3 presents the tests, Section 4 justifies the design decisions, and Section 5 concludes.

== Methodology

=== System Architecture

The code base is one Python package, `yazilim_lab_project`, with four parts (Fig. 1).

* `models/` contains the typed data structures: the initial data, reservations, waiting entries, application state, commands, results and events.
* `rules/` contains validation only. Small predicates are in `rules/atomic/`. Each command has an `all_rules_*` function that runs the predicates in the specified order and returns `Ok(data)` or `Err(code)`. Rules never change the state.
* `interface/` contains the functions that change the state (entry, exit, no-show, cancellation, waiting-list scan, clock advance) and the price calculation.
* `interface/engine.py` contains the class `Engine`. `Engine.execute(command)` dispatches a typed command with structural pattern matching, calls the matching rule function, applies the state change only if the rules returned `Ok`, and returns a typed result. The engine does not read or write files.

*Interaction with the desktop application.*
The command-line path parses each line of the command file into a typed command object (`CommandsFile`) and passes it to the engine.
The desktop application does not read a command file.
When a start file is selected it builds a new `AppState` and a new `Engine`; every user action creates the same typed command object and calls `Engine.execute`; the returned result is displayed.
A price preview uses `execute(PriceCommand, record=False)`, which does not change the state and is not logged.
The engine keeps a history of `(command, result)` pairs, which is the data source for the event log.
The application contains no business rule: even an invalid request is sent to the engine, which returns the error code.

The simulated clock is stored in `config.time`.
Derived values (occupancy, price, waiting position) are computed when needed and are never stored, so no cache can become outdated.
Reservation identifiers are generated from the number of reservations, which is valid because reservations are never deleted.
Package identifiers are the largest existing package number plus one.
Waiting identifiers use a separate counter (`next_waiting_id`), because waiting entries are removed when they are promoted or expire, and an identifier must never be reused.

=== Application of the Rules

*Validation order (K10).*
A reservation request passes thirteen checks in a fixed order and the code of the first failing check is returned (Algorithm 1).
All intervals are half-open, `[start, end)`.
Two intervals _a_ and _b_ intersect if `a.start < b.end` and `b.start < a.end`.
The preparation check widens the existing reservation by the preparation time _h_ of the resource type on both sides, and the consecutive-use check does the same with 60 minutes for the same user and resource.
The status of the existing reservation decides whether it is counted (Table 2).
The price is computed only after all other checks have passed, because the balance check is the last one.

.Reservation states counted by each check
[cols="3,5",options="header"]
|===
| Check | Counted states
| KESISME | ONAYLI, KULLANIMDA
| HAZIRLIK_IHLALI, ARDISIK_KULLANIM | ONAYLI, KULLANIMDA, TAMAMLANDI
| Occupancy for pricing | ONAYLI, KULLANIMDA (same resource type)
| All checks | IPTAL and GELMEDI are never counted
|===

*Pricing (K5).*
The price is calculated for every 15-minute slice _s_ of the request (Algorithm 2):

[stem]
++++
\text{price}=\operatorname{round}_{\uparrow}\Big(\sum_{s}\; B\cdot 0.25\cdot m_{band}(s)\cdot m_{peak}(s)\Big),\quad
m_{band}=1+0.25\,\lfloor 4\rho \rfloor,\quad
\rho=\frac{\text{occupied minutes in band}}{n_{type}\cdot 120}
++++

where _B_ is the base hourly fee of the type, _n~type~_ is the number of resources of that type at the moment of the request, and `round↑` rounds half up.
The day is divided into seven two-hour bands (08-10, ..., 20-22).
The occupancy of a band is the sum of the minutes of ONAYLI and KULLANIMDA reservations of the same type that lie inside the band; the request itself and maintenance windows are not counted.
The peak multiplier is 1.5 for energy-intensive types between 10:00 and 16:00, otherwise 1.0.
Python's built-in `round` uses banker's rounding, so the final rounding is done with `decimal.Decimal` and `ROUND_HALF_UP`.
All multipliers are multiples of 0.25, so the floating-point sums are exact.

*Balance and weekly quota (K6).*
The price is deducted when the reservation is accepted.
When the clock passes a Monday 00:00, every balance is _set_ to the weekly quota of the user's role; unused points are not carried over.
A refund is limited so that the balance never exceeds the quota: `credited = min(quota, balance + refund) - balance`, and this credited value is the refund reported in the result.

*State machine and reliability (K8).*
Table 3 summarizes the transitions.
Entry is allowed from 10 minutes before to 15 minutes after the start time (otherwise GIRIS_PENCERESI_DISI).
Entry, exit and cancellation check BULUNAMADI first and DURUM_HATASI second; entry then checks the time window.
A reliability below 50 reduces the booking horizon to one day and forbids packages.

.Transitions, refunds and reliability changes
[cols="4,3,2",options="header"]
|===
| Event | Refund | Reliability
| Cancel, 24 h or more before start | 100% | unchanged
| Cancel, from 2 h up to 24 h before start | 50%, rounded down | unchanged
| Cancel, less than 2 h before start | 0 | -5
| No-show (no entry until start + 15 min) | 0 | -15 (minimum 0)
| Completed at the end time | -- | +2 (maximum 100)
| Early exit (`cikis`) | none, end time := now | unchanged
|===

*Package reservations (K7).*
A package of two to four items is accepted completely or not at all.
Checks run in this order: BULUNAMADI, PAKET_BOYUTU, GUVENILIRLIK_DUSUK, PAKET_RED, PAKET_ICI_KESISME, BAKIYE_YETERSIZ.
Each item is validated separately with the K10 checks except the balance check, and the status of every item (TAMAM or the code) is returned in the result.
Items are priced against the state before the package, so other items of the same package do not raise the occupancy.
Conflicts between items of the same package (intersection, preparation time, consecutive use) are detected pairwise.
The state is changed only after all checks have passed: the total is deducted once and all reservations get the same package identifier.

*Waiting list (K9).*
A waiting entry is accepted only when the request fails because of KESISME or HAZIRLIK_IHLALI; any earlier failure returns its own code, and a request that is already valid returns BEKLEME_GEREKSIZ.
The balance is not checked at this point.
When a resource becomes free (cancellation, no-show or early exit) the list of that resource is scanned (Algorithm 4).
Candidates are ordered by reliability (high first), then by registration time, then by the numeric part of the identifier (b2 before b10).
Every candidate goes through the complete K10 validation with the current clock and balance; a candidate that passes becomes a reservation at the current price, the others stay in the list, and the scan continues to the end.
Entries whose start time has passed are deleted.
Automatic completion by the clock at the end time does not trigger a scan, because the time it frees is already in the past; an explicit exit does.

*Simulated clock (K11).*
`advance_clock` collects all events in the interval (old time, new time], including an event exactly at the new time (Algorithm 3).
Events are placed in a priority queue ordered by time, then by type priority (weekly reset, completion, no-show), then by the numeric reservation number.
For each instant the clock is first moved to that instant, because the waiting-list scan uses the clock for timestamps and for the removal of expired entries.
After the weekly resets, completions and no-shows of that instant, the waiting lists of the freed resources are scanned once per resource.
A reservation created by an automatic assignment may itself become a no-show inside the same window, so its no-show is added to the queue immediately.
A new time before the current time returns SAAT_GERI.

=== Pseudo-code and State Machine

[[alg-validate]]
.Validation of one reservation request (K10)
[source,text]
----
function VALIDATE(u, r, b, e, S):
  if u or r unknown:                       return BULUNAMADI
  if b mod 15 != 0 or e mod 15 != 0
     or e <= b:                            return ZAMAN_ADIMI_HATASI
  if b < S.clock:                          return GECMIS_ZAMAN
  if b < 08:00 or e > 22:00 (same day):    return CALISMA_SAATI_DISI
  if e-b < 30 min or e-b > role(u).max:    return SURE_SINIRI
  H <- 1 day if rel(u) < 50 else role(u).future_day
  if b > S.clock + H:                      return ILERI_TARIH_SINIRI
  if role(u) not in r.allowed_roles:       return ROL_IZNI_YOK
  if type(r) needs cert and u lacks it:    return SERTIFIKA_YOK
  if overlaps maintenance window of r:     return BAKIM
  if overlaps ONAYLI/KULLANIMDA on r:      return KESISME
  if exists x in {ONAYLI,KULLANIMDA,TAMAMLANDI} on r with
        b < x.e + h and x.b < e + h:       return HAZIRLIK_IHLALI
  if same rule with +60 min, x.user == u:  return ARDISIK_KULLANIM
  p <- PRICE(r, b, e, S)
  if p > bal(u):                           return BAKIYE_YETERSIZ
  return OK(p, bal(u) - p)
----

[[alg-price]]
.Price of a request (K5)
[source,text]
----
function PRICE(r, b, e, S):
  total <- 0
  for t in b, b+15min, ..., e-15min:
    band  <- [t - (t.hour mod 2)h - t.minute, +2h)
    busy  <- sum of overlap(x, band) for x in S.reservations
             with x.state in {ONAYLI, KULLANIMDA}
             and type(x.resource) = type(r)
    rho   <- busy / (count(resources of type(r)) * 120)
    mband <- 1 + 0.25 * floor(4 * rho)
    mpeak <- 1.5 if energy_intensive(type(r))
                    and 10:00 <= t < 16:00 else 1
    total <- total + base_fee * 0.25 * mband * mpeak
  return ROUND_HALF_UP(total)
----

[[alg-clock]]
.Advancing the simulated clock (K11)
[source,text]
----
function ADVANCE(S, T):
  Q <- min-heap ordered by (time, priority, seq)
  push (Monday 00:00 in (S.clock, T],  0, weekly)
  for x in S.reservations:
    if x.state = KULLANIMDA and S.clock < x.end <= T:
        push (x.end, 1, complete x)
    if x.state = ONAYLI and S.clock < x.start+15 <= T:
        push (x.start+15, 2, no-show x)    # ties: numeric id
  while Q not empty:
    t <- time of Q.top;  S.clock <- t;  freed <- []
    for each job at time t, in heap order:
      weekly   : bal(u) <- quota(role(u)) for all users
      complete : x.state <- TAMAMLANDI; rel <- min(100, rel+2)
      no-show  : x.state <- GELMEDI;    rel <- max(0, rel-15)
                 freed.add(x.resource)
    for r in unique(freed): events += WAITSCAN(S, r)
    for each reservation y created in this step:
      if y.start+15 <= T: push (y.start+15, 2, no-show y)
  drop waiting entries with start < T;  S.clock <- T
----

[[alg-wait]]
.Waiting-list scan for a freed resource (K9)
[source,text]
----
function WAITSCAN(S, r):
  drop waiting entries with start < S.clock
  C <- entries of r sorted by (-rel(user), registered_at, numeric id)
  for w in C:
    res <- VALIDATE(w.user, r, w.start, w.end, S)   # full K10
    if res = OK(p, bal'):
      bal(w.user) <- bal';  create ONAYLI reservation (price p)
      remove w;  emit OTOMATIK_ATAMA
  # entries that fail stay in the list
----

== Experimental Results

*Test strategy.*
The suite consists of 16 test functions in 13 files, one file for each command family (`kullanici_ekle`, `kaynak_ekle`, `rezervasyon`, `fiyat`, `paket`, `bekleme`, `saat`, `giris`, `cikis`, `iptal`, `sorgu` for users and for resources) and one end-to-end scenario.
Most tests are data driven.
A folder `tests/data/<area>/` holds `initial_data.json`, a JSON Lines command file and a JSON Lines file with the expected results.
The test builds the state, seeds reservations or waiting entries that are difficult to reach by commands, replays the commands and compares every produced result with the expected one as a typed object, so every field of the result must be equal to the expected value.
The end-to-end test `test_full` replays a complete command file through `Engine.execute` and compares the whole result list.

== Design Decisions

*Language and data validation.*
Python 3.11 offers structural pattern matching, `StrEnum` and the `decimal` module, which fit the problem.
Pydantic v2 validates every input at the boundary.
Discriminated unions select the command class from the field `komut`, the event class from `tur` and the result class from `durum`, so a malformed line fails immediately.
Aliases keep the Turkish JSON names of the specification while the code uses English names, and the same typed models serve as the test oracle.

*Rules as read-only functions with a result type.*
A rule failure is an expected outcome, so rule functions return `Ok` or `Err` values instead of raising exceptions, and they never change the state.
The engine changes the state only in the `Ok` branch, which makes packages and automatic assignments atomic.
The same small predicates (`atomic_rule_reservation_*`) are shared by the reservation rules, the waiting rules and the waiting-list scan, so they cannot drift apart.

*One engine without input or output.*
All behavior is reachable through `Engine.execute`.
The command-line runner and the desktop application only translate between their own input and output and the typed commands and results, which guarantees that the screen shows the same results as the result file.
The `record` flag allows a price preview without a log entry, and the history list supports the event log.

*Clock and numbers.*
The clock first collects all jobs and then consumes them from a heap, so decisions are based on one consistent snapshot and the K11 order is a single sort key.
Reservation numbers are compared as integers because text order would put r10 before r2.
Prices and balances are integers; the pricing sum is exact for the allowed multipliers and is rounded with an explicit `ROUND_HALF_UP`.

*Data structures.*
The state is kept in plain lists in memory, as the project allows, and searched linearly.
For a campus-sized data set this is fast enough; the pricing cost grows with the number of slices times the number of reservations, and indexes by resource and day are a simple improvement if the data grows.

== Conclusion

We implemented the reservation module of the Campus Resource Reservation System: the thirteen-step validation, maintenance, preparation and consecutive-use rules, occupancy-based pricing, the weekly quota, atomic packages, the state machine with refunds and reliability, the reliability-ordered waiting list with automatic assignment, and the deterministic simulated clock.
All behavior is available through one engine without file input or output, and a data-driven test suite covers each command family and the difficult interactions between them.

The main difficulties were details that the rules leave to the implementer: the order of simultaneous events, an automatic assignment that creates a new event inside the window being processed, identifiers that must not be reused, integer ordering of identifiers, and exact half-up rounding.
Each of them is covered by a dedicated test.

*Future work.*
The command-line runner (`calistir.sh` and `calistir.bat`) and the desktop application remain to be completed and verified against the sample scenario (TODO: update this paragraph when they are finished).
The package rules repeat the item checks of the single-reservation rules because each item must report its own status; they can be merged into one shared implementation.
A circular import between the rules and the waiting-list functions (the waiting-identifier parser) should be moved to a neutral module.
Indexes and an optional persistent store would allow larger campuses.
