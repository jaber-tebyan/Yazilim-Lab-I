## 6. `cikis` does not trigger the waiting-list scan (K9)

- [x] Fix

**Where**
- `src/yazilim_lab_project/interface/reservation.py` → `exit_reservation`
- `tests/test_exit.py` → hardcodes `events=[]`
- `src/yazilim_lab_project/models/results/ExitResult.py` → TODO comment says the
  document does not mention `events`, but it does

**Problem**
K9 says a resource's waiting list is scanned when a slot is freed by **iptal,
gelmeme or çıkış**. `exit_reservation` only changes state/reliability and never
calls `process_waiting_list_for_resource`, so `cikis` never produces
`OTOMATIK_ATAMA` events. The result model has an `events` field, but it is
always empty in the test.

**Expected**
- `cikis` frees the resource and scans its waiting list.
- The resulting `OTOMATIK_ATAMA` events are returned in the `cikis` result's
  `olaylar` field (document line 723: `yeni_durum, guvenilirlik, olaylar`).
- The scan follows the same ordering as cancel/no-show: reliability desc,
  `kayit_saati`, then numeric waitlist id.
- Remove the incorrect TODO comment in `ExitResult.py`.

**Do not break**
`interface/clock.py` `_apply_completion` also calls `exit_reservation`.
Time-driven completion must **not** scan the waiting list (K9 triggers are only
iptal, gelmeme, çıkış). Either:
- add a parameter such as `scan: bool = True` and pass `scan=False` from the
  clock, or
- split the state change from the scan and let `cikis` call the scan.

**Tests**
- Add a waiting entry for the exited reservation's resource in
  `tests/data/exit/` and assert the auto-assign event in `results.jsonl`.
- Keep/verify a clock test that proves completion still does not scan.

## 7. Waiting-list IDs can collide

- [x] Fix

**Where**
- `src/yazilim_lab_project/rules/waiting_rules.py` →
  `waitlist_id = f"b{len(state.waiting_list) + 1}"`

**Problem**
Waiting entries are deleted when promoted or expired. Using the current list
length as the next id means an id can be reused while it still exists.

Example: list `[b1, b2, b3]`; `b1` is promoted → `[b2, b3]`, length 2 → next id
is `b3`, which already exists.

**Expected**
IDs are `b1, b2, ...` in creation order (document line 296) and never collide.
Use a monotonic counter, for example:
- `max(parse_waitlist_id(w.id) for w in state.waiting_list) + 1`, or
- a dedicated counter on `AppState`.

Keep `parse_waitlist_id` numeric (`b2` before `b10`).

**Tests**
Add a case where an earlier entry is promoted/expired and a new waiting entry
is created afterwards; assert the new id does not collide.

## 9. Waiting validation order deviates from K10

- [x] Fix

**Where**
- `src/yazilim_lab_project/rules/waiting_rules.py` → `all_rules_waiting`

**Problem**
The function checks `ARDISIK_KULLANIM` before `KESISME` / `HAZIRLIK_IHLALI`.
K10 order is:

```
... 9 BAKIM
    10 KESISME
    11 HAZIRLIK_IHLALI
    12 ARDISIK_KULLANIM
    13 BAKIYE_YETERSIZ
```

If a request both intersects an existing reservation and violates consecutive
use, the first failing K10 step is `KESISME`, so a waiting entry should be
allowed. The current code returns `ARDISIK_KULLANIM` instead.

**Expected**
Evaluate the checks in K10 order and return the **first** failure:
- if the first failure is `KESISME` or `HAZIRLIK_IHLALI` → create the waiting
  entry;
- if the first failure is anything else → return that error code;
- if nothing fails → `BEKLEME_GEREKSIZ`.

Balance is intentionally not checked when opening a waiting entry (K9).

**Tests**
Add a case where the request fails both KESISME and ARDISIK; expect a waiting
entry to be created (not `ARDISIK_KULLANIM`).
